结论摘要

结果代表本机 Chromium、1280×720、未开启网络或 CPU 节流、禁用 HTTP 缓存时的生产 Preview 表现，不能直接替代公网真实用户监控。

总体判断：首屏渲染快，所有采样接口均成功；主要风险不在渲染，而在共享包体积和管理页按仓库逐个请求造成的 API 扇出。
  • FCP P75 为 88 ms，LCP P75 为 236 ms；最大 LCP 668 ms，出现在 管理总览。
  • 单路由冷加载最多传输 462.5 KB；完整构建产物 gzip 合计 493.8 KB。
  • 访问控制 40 个 API，任务中心 40 个 API，请求数会随仓库规模线性增长。

问题与优化建议

高优先级：收敛管理查询扇出

  • 访问控制逐仓库读取 /grants，任务中心逐仓库读取 /lifecycle-jobs，本次均达到约 40 个 API。建议提供批量摘要端点，页面仅在展开单仓库时加载详情。
  • 总览和仓库列表逐仓库读取容量，最慢请求达到 270 ms；建议增加 capacity batch/summary 接口，并为慢仓库设置独立超时与渐进呈现。
  • 管理 Shell 还会发起 /repositories?pageSize=1 会话探针，可改为轻量 /me 或复用页面 bootstrap，减少一次往返。

中优先级：缩小公开入口共享包

  • 最大共享 chunk 是 antd，原始 960.3 KB、gzip 308.1 KB；公开浏览页同样加载该依赖。
  • 建议把管理端 Ant Design 组件和图标延迟到登录后的路由，并复查图标及组件导入是否形成整包依赖。

持续基线

  • 在 CI 保存 FCP/LCP、API 数量与产物 gzip 历史，对包体和请求扇出设置回归阈值。
  • 线上补充 Web Vitals、API p95 与错误率；本地无节流结果不等于公网体验。
