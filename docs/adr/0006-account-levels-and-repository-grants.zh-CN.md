# 账号等级与按仓库授权

[English](0006-account-levels-and-repository-grants.md) · [文档索引](../README.zh-CN.md)

状态：已接受

## 背景

仓库权限此前来自每个账号唯一的全局角色。两个性质使它无法用来限制访问范围：

- 角色判定**忽略目标仓库**，因此 `reader` 意味着所有仓库，`writer` 意味着对所有仓库读
  写；
- 角色在按仓库授权**之前**判定，因此一个全局 `writer` 会让那些授权对读与写失去意义。
  "把某账号限定在特定仓库"根本无法表达。

管理权限形态相同。单一的 `administrator` 布尔值门禁整个管理面，且所有凭据来源都把它推
导为 `role == admin`，因此无法只授予仓库管理而不授予全系统管理。按仓库的
`repositories:admin` 作用域**早已存在**并已接入各仓库的管理操作，但它只能作为授权存在，
不能作为账号分配。

另有两处相关行为是**文档化的姿态而非疏漏**：仓库列表仅管理员可见，以及未配置 reader
模式的部署会放行任何已认证调用方。两者都在此被限定或改写，因此文档随代码一起移动。

## 比较过的方案

### 1. 保留四个全局角色，另加可选的仓库范围

分配时携带仓库子集，未限定者保持今天的含义。兼容性最好，但模型里会长期并存两种回答
"这个账号能触及什么"的语义——而这正是要消除的歧义。读者必须知道某账号是以哪种形式创
建的。

### 2. 保留四级，作为授权之上的上限

等级限定"最多能做什么"，授权限定"在哪里能做"。这样能得到一句明确的"该账号永不可写"，
但 `reader` 上限会静默切断既有的 `repositories:write` 授权——这是旧模型允许、且现网可能
存在的组合。迁移必须反过来提升等级并报告被改动的实例。

### 3. 三级等级，仓库权限完全来自授权

等级回答"这个账号是否存在"，授权回答"在哪里、能做多少"。唯一的反对理由是迁移既有全局
角色的成本，而下面的迁移把它吸收掉了。

## 决定

**等级。** 账号等级为 `none`、`member`、`admin`。`member` 不附带任何隐式仓库能力：等级
本身不放行任何仓库操作，因此授权是仓库权限的唯一来源。`admin` 是平台管理员，保留既有
管理面。

**授权为其命名的主体作决定。** 显式命名某主体的条目即使在该 grant set 未被标记为托管
时也生效；未命名该主体的集合仍走 legacy 静态策略。这正是"物化授权而不必把每个仓库标记
为托管"得以成立的原因——否则那些仅持 legacy 静态策略的主体会被切断。

**`none` 是硬性拦截。** 处于 `none` 的账号即使被显式授权也被拒绝，因此"待审批"无法被授
权绕过。批准意味着设置等级。

**两档管理，其中一档是新引入的。** 平台管理员即 `admin` 等级。仓库管理员是持有某仓库
`repositories:admin` 的 `member`。改变仓库对所有客户端行为的操作——仓库配置与删除——
要求该作用域而非 `write`，后者只管辖发布与删除制品。

**迁移。** 既有 `reader` 与 `writer` 账号在升级时被转换为 `member`，并在当时已存在的仓
库上获得等价授权；不把任何 grant set 标记为托管，因此 legacy 静态读写主体继续可用。

**legacy 读取默认值改为拒绝。** 未配置的部署会拒绝未匹配的已认证调用方，而 0.3.1 及
更早版本正是静默放行了这类调用方。`GATEWAY_LEGACY_READ_DEFAULT=allow` 作为迁移辅助可
恢复此前的姿态，并在设置期间打印启动告警，使运营商在必须盘点无授权读取主体时能分阶段
升级，而不是让读取无预警地中断。无法识别的取值按拒绝处理。

## 后果

分配一个角色不再等于交出所有仓库。范围成为独立的、按仓库的决定，调用方看到的目录恰好
是其授权允许的集合，因此空结果不再泄露仓库是否存在。

升级之后新建的仓库**不被迁移覆盖**：对新仓库的访问是显式授权，而不是继承来的副作用。
这是刻意的收紧而非迁移缺口，也意味着"我能读全部"这一便利变成由管理员执行的一次批量
分配。

`reader` 与 `writer` 等级会再被接受一个版本，以免升级打断用它们建号的外部自动化。移除
它们是另一项变更，把 Console 的角色选择器收敛为三个等级同样是另一项。

管理面仍是单一平台档。把它拆成平台与仓库两档被推迟：接缝已在 issue 跟踪中画出，而按仓
库的那部分已有可用的作用域作为基础。

Console 现在有三处授权编辑器。用户侧的分配视图被推迟到抽出共享编辑器之后，因为第三份
内联实现会与前两份漂移。写路径也需要"读取-合并-写回"的编排，因为替换某仓库的授权会替
换整个集合。
